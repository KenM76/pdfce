# type3 — provenance and attribution

Single-page PDF fixtures for **Type 3 fonts** — ISO 32000-1 §9.6.5, the one
font subtype whose glyphs are **content streams** rather than a font program.
Rendered by `crates/pdfce-render/src/type3.rs` and
`crates/pdfce-render/src/interpret.rs`'s `show_type3`; used by
`crates/pdfce-render/tests/type3_fonts.rs`.

## Source material and license (LEGAL.md §5, project rule 7)

**Nothing here derives from a third-party file.** These are `LEGAL.md` §5
category (a): **wholly synthetic**, authored for this project, generated by a
committed script (`tools/gen-type3-fixtures.py`) from geometry this project
chose — filled rectangles and one 8×8 bitmap. No attribution is owed or
claimed, and nothing was downloaded from anywhere.

The PDFs are assembled **byte by byte** from a classic §7.5.4 cross-reference
table with no object streams and no compression, so a failing test can be
diagnosed in a hex editor and a fuzzer mutating one keeps producing something
a parser will engage with.

## What each file is for

Every file is 612 × 720 pt. The Type 3 font uses the conventional
`[0.001 0 0 0.001 0 0]` matrix, so at 40 pt a 700-unit box is 28 pt and a
750-unit advance is 30 pt — two numbers a test can measure two points apart.

| file | what it provokes | what only it can catch |
|---|---|---|
| `colour_and_advance.pdf` | `d0` vs `d1` colour, the image-mask flavour, and the advance | a renderer that honours a `d1` procedure's own colour, that collapses `d0` and `d1` into one, or that divides a Type 3 width by 1000 |
| `missing_glyph_advances.pdf` | a code named in `/Differences` and **absent from `/CharProcs`**, between two that are present | a renderer that treats a missing glyph as a skipped code, which mis-positions every later glyph on the line |
| `resources_fallback.pdf` | a font with **no `/Resources`** whose glyph invokes a form XObject by name | Table 112's page-resource fallback, which old files depend on and whose absence reports "resource not found" on a well-formed document |
| `self_recursive.pdf` | a glyph procedure that shows its own font | an unbounded reader — this input is a stack overflow by construction, and §9.6.5 permits it |

## The controls are the design

★ **Every assertion here is paired with one that must come out differently.**
A `d1` glyph coming out blue proves nothing on its own: a renderer that
painted every Type 3 glyph in the text colour would pass it. It is the `d0`
twin coming out **red** — from the identical colour operator, on an identical
box, over the identical page colour — that carries the result.

The same reasoning shapes the rest:

- `colour_and_advance.pdf`'s **row B** (a `d1` glyph with no colour operator
  at all) is what licenses reading row A as a result rather than as a
  coincidence.
- The `type3_colors_ignored` counter must read **1**, not 2: the fixture holds
  two colour operators inside glyph procedures, one in a `d1` (ignored) and
  one in a `d0` (honoured). A renderer that suppressed both reports 2, one
  that suppressed neither reports 0, and only a correct one reports 1.
- `self_recursive.pdf` asserts both that the render **terminates** and that it
  **drew something** — a reader that refused Type 3 outright, or bailed at the
  first nesting, also terminates.

★★ **Row E was added after rows A–D, and the reason is worth keeping.** The
first four rows position every glyph with `Td`, so a renderer that ignored
`/Widths` entirely would render them perfectly. Row E shows **four glyphs in
one string**, which is the only way the pen is moved by the width and by
nothing else. A fixture that avoids a feature's precondition cannot tell a
correct implementation from one that does not have the feature.

## Rows A–D are also the Acrobat oracle

`colour_and_advance.pdf`'s first four rows were rendered in **Acrobat Reader
on 2026-08-25**, to answer a question the Acrobat-parity corpus had recorded
as an open `GAP`: no source established whether Acrobat honours §9.6.5's rule
that a `d1` procedure's colour operators "shall be ignored", or lets the
procedure win.

It honours it — row A **blue**, row C **red**, row D **blue** with the stencil
correct. So Acrobat is spec-conformant on every point this fixture tests, and
an acceptance criterion citing §9.6.5 is simultaneously an Acrobat-parity
criterion. Recorded in
`D:\Dev\Rag-Specialized\Acrobat_Features\type3fonts__rendering_and_color_semantics.md`.

That measurement is deliberately **not** re-run as a test: it is a fact about
another program on one machine on one day, and pinning it in `cargo test`
would make this suite fail when Acrobat changes rather than when pdfce does.

## How to regenerate

```
python tools/gen-type3-fixtures.py
```

The script is the authority; these files are its output and are checked in
only so that `cargo test` needs no Python.
