# overprint — provenance and attribution

Single-page PDF fixtures for **ISO 32000-1 §11.7.4.3 `CompatibleOverprint`
applied to a SAMPLED IMAGE** — Table 149's `Separation`/`DeviceN` row, which
`Pass 130.2` wired up (`Canvas::fill_image_overprint`,
`Interpreter::paint_image_overprint`). Used by
`crates/pdfce-render/tests/overprint_image.rs`.

**★ In particular, no byte of the licensed print-conformance suite is

that found the defect and the oracle that scored the fix — three of its
patches went from FAIL to pass — but it is not redistributable, it is not in
this repository, and it is not on a fresh clone or on CI. These files are the
committed half of the evidence: the shapes below are read off **Table 149**,
not off any patch, and they use a colorant set (`/Black` over a cyan-plus-black
backdrop) that no patch uses, for the reason the generator's docstring gives.

The PDFs are assembled **byte by byte** from a classic §7.5.4 cross-reference
table with no object streams and no compression on the structure, so a failing
test can be diagnosed in a hex editor and a fuzzer mutating one keeps producing
something a parser will engage with.

## The six files

Every one is 100 × 100 pt and paints the same 40 × 40 pt mark at (30, 30) over
the same 80 × 80 pt `1 0 0 1 k` backdrop — 100 % cyan **and** 100 % black.
They differ in exactly one variable each.

| file | mark | page group | colorants | `/OP` | expected |
|---|---|---|---|---|---|
| `devicen_op_cmyk.pdf` | image | `/DeviceCMYK` | `[/Black]` | true | **cyan** — `K` takes the source's 0, `C`/`M`/`Y` survive from the backdrop |
| `devicen_op_path_cmyk.pdf` | **path** | `/DeviceCMYK` | `[/Black]` | true | **the same pixels as the row above** |
| `devicen_noop_cmyk.pdf` | image | `/DeviceCMYK` | `[/Black]` | **false** | **white** — Table 148/149's `c_s (= 0.0)`: overprint OFF *erases* the colorants the source does not name |
| `devicen_all4_op_cmyk.pdf` | image | `/DeviceCMYK` | `[/Cyan /Magenta /Yellow /Black]` | true | **white** — naming every process colorant makes overprint inert |
| `sep_devicen_op_rgb.pdf` | image | *(none)* | `[/Black]` | true | the sRGB arm of the same composite |
| `devicen_op_path_rgb.pdf` | **path** | *(none)* | `[/Black]` | true | **the same pixels as the row above** |

### ★ Why the two `_path_` twins are the load-bearing pair

Because they need **no reference render and no remembered constant**.
§11.7.4.3 is written about a source *colour*, not a source *object*, so an
overprinting `/DeviceN [/Black]` rectangle and an overprinting
`/DeviceN [/Black]` image of the same tint over the same backdrop must land on
identical pixels. Before `Pass 130.2` they did not: the rectangle went through
`paint_overprint` and came out cyan, the image went through an ordinary paint
and came out white. **Nothing but a comparison of the two could say which one
was wrong** — which is why both halves are on disk rather than one file with an
expected colour written into a test (`R215`, the wrong-oracle shape).

### ★ Why the additive pair does not come out cyan, and that is not a bug

On `sep_devicen_op_rgb.pdf` both twins render `(0, 22, 255)` rather than the
cyan the subtractive pair gives. That is `overprint::composite`'s documented
limitation and it is **symmetric across the two twins**, which is the whole
point of committing them together: an additive canvas has no colorant planes,
so the backdrop's component split is *reconstructed* by `rgb_to_cmyk`, and a
`100C + 100K` backdrop reconstructs as `C = 1, M = 0.914, Y = 0, K = 0.863` —
the same colour by a different route. Preserving that `M` is what turns the
result blue. A renderer that "fixed" it by converting differently would break
the round-trip property `rgb_to_cmyk`/`cmyk_to_rgb` exist to guarantee.

The real fix is the per-colorant buffer, which the subtractive pair already
demonstrates: give the page a `/DeviceCMYK` group and the ambiguity disappears,
because the planes *are* the backdrop.
