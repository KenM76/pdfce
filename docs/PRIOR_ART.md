# pdfce — Prior art & candidate open-source dependencies

Living survey of existing open-source projects/crates pdfce can lean
on — either as real dependencies (properly licensed and credited) or
as read-only architectural/behavioral reference. Maintained by
`pdfce-engineer` (dispatch `pdfce-librarian` for the actual file
edits, same discipline as `ARCHITECTURE.md`'s decision log). See
`docs/LEGAL.md` §6 for the binding licensing/attribution rules this
document exists to support.

**Distinct from `THIRD_PARTY_LICENSES.md`** (doesn't exist yet — it's
generated by `cargo-about` from the real `Cargo.lock` once dependencies
are actually added, see `LEGAL.md` §6.3). This file is the *research
and decision record*; that file is the *mechanically generated
compliance artifact*. Keep both, don't conflate them.

**Status**: first full research pass complete, 2026-07-23 (three
parallel surveys, web-verified — not training-data recall). All
license SPDX IDs below are per-session-verified unless flagged
otherwise. **Re-verify anything used for a real dependency decision
if this file is more than ~6 months old at the time** — crate
maintenance status and licensing terms both drift, and one entry
below (Poppler) is already flagged unresolved.

## OPEN QUESTION — resolve before scaffolding pdfce-core from scratch (Pass 0 blocker candidate)

**`oxidize-pdf`** (github.com/bzsanti/oxidizePdf, MIT, v4.2.1 as of
2026-07-22) claims to already cover nearly all of `pdfce-core`'s
target scope: COS parsing (99.3% claimed success on 9,000+ real
PDFs), xref tables + streams, object streams, **incremental updates**,
RC4-40/128 + AES-128/256 (R5/R6) encryption read/write, PKCS#7
signature **verification**, pure-Rust JBIG2/CCITT/DCT/JPX, PDF/A
validation, 7,993 tests claimed. Single-maintainer project (bus-factor
risk, claims not third-party-audited), marketed toward "AI/RAG" text
extraction rather than general editing, so full object-model fidelity
for a true editor is unverified beyond its own numbers.

**Action before Pass 1 (not yet decided — flag to the user, don't
decide solo):** dedicated audit of `oxidize-pdf` against pdfce-core's
actual requirements (round-trip fidelity on adversarial/malformed
input, signature-safe incremental-save semantics specifically, PAdES
signing not just PKCS#7 verify) to decide: adopt as foundation, vendor
+ audit, or treat as reference-only and build independently. This is
the single highest-leverage decision in this whole survey — it could
change `ARCHITECTURE.md` §3/§4 materially. **Do not silently default
to "build from scratch" without this audit having happened.**

"Existing full OSS PDF tools" below for **Open PDF Studio** and

**Confirmed cross-report: no mature, actively-maintained, general-
purpose Rust crate exists for PAdES-conformant signing.** Build from
`cms` + `x509-cert` + RustCrypto signature primitives + a timestamping
(RFC 3161) client. `open-pdf-sign` (Java, Apache-2.0 + an LGPL-2.1
`dss` subfolder, github.com/open-pdf-sign/open-pdf-sign) supports full
PAdES B/T/LT/LTA baseline profiles — wrong language to depend on, but
the single best **architecture/spec reference** found for what
complete PAdES support actually requires.

### Competitive-landscape bottom line

**No existing open-source project — web or desktop — currently
combines the full breadth pdfce targets** (editing + forms +
signatures + true redaction + OCR + Bates + PDF/UA tagging + PDF/A +
portfolios + comparison + optimization) in one native desktop
application. Stirling-PDF has the widest feature breadth but is a web
app with an open-core (non-fully-FOSS) license. Open PDF Studio is the
nearest native-desktop attempt (and validates a "thin Rust shell +
PDFium/PDF.js rendering" pattern) but lacks OCR/Bates/PDF-A/
accessibility-tagging. KillerPDF proves OCR+forms+signing+repair is
deliverable natively without a huge codebase, but is GPL-3.0
(code-reuse-blocked) and Windows-only. **pdfce's scope remains
substantially greenfield, particularly for OCR integration, PDF/UA
tagging, Bates stamping, PDF/A/PDF/X conversion, true-removal
redaction, and portfolios.** This validates the project's premise —
worth a one-line pointer from `ARCHITECTURE.md` §1 (added, see its
decision log).

## Copyleft landmines (read this before touching MuPDF/Ghostscript/Poppler source)

- **MuPDF and Ghostscript (both Artifex, both AGPL-3.0[-or-later])**:
  linking either into pdfce forces pdfce itself to AGPL-3.0 for that
  build, or requires purchasing Artifex's commercial license. This is
  a **project-defining decision**, not a routine dependency pick —
  never back into it via a library choice; if it ever becomes
  attractive (e.g. for rendering fidelity), it's a "stop and ask the
  user" moment per `LEGAL.md` §6.2.
- **Reading AGPL/GPL source for algorithmic understanding, then
  writing independent Rust code, carries low practical risk** —
  copyright/copyleft attaches to *expression*, not to ideas/algorithms.
  Risk becomes real if code is transliterated closely enough to
  constitute a derivative work (same distinctive structure/comments/
  variable choices), or if the same person who read the copyleft
  source writes the "independent" version from memory in a way that
  reproduces it closely. **For anything algorithmically close to
  MuPDF/Ghostscript/Poppler's own approach, consider a formal
  clean-room split (one person/session reads + writes a spec, a
  different one implements from the spec only)** — flag this
  explicitly to the user if it comes up for a specific feature, this
  is not a routine engineering call.
- **Poppler's exact license is the one important unresolved fact in
  this whole survey** — treat as GPL (strict, not LGPL) until a direct
  COPYING-file check confirms otherwise.
