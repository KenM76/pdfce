# Icon-asset provenance

Owed by `docs/ui_specs/icon-set-and-toolbar.md` §7.2, which required the
provenance of this icon set to be **confirmed, not assumed**, before any
art was bundled into pdfce.

## 1. Operator confirmation (the licensing question, closed)

The ui-spec flagged an open question: were `D:\Dev\ScripTree\icons\*.svg`
drawn from scratch for ScripTree, or adapted from a third-party icon
pack (Feather, Lucide, Font Awesome, …) whose own licence would then
travel with them into pdfce's asset tree?

Answered directly by the operator (Ken), 2026-08-02, verbatim:

> "Scriptree icons are mine, use from it what makes sense and create new
> ones in its style when necessary, try to make them close to what
> inkscape and Adobe use for similar commands without running into
> copyright issues."

Consequences, all of them binding on this directory:

* The ScripTree source art is the operator's own work. He owns both
  projects, so no third-party licence travels with the copied files and
  nothing here needs an upstream attribution entry.
* pdfce's own licence is MIT (`docs/LEGAL.md` §1, decided 2026-08-01);
  these assets ship under it like the rest of the tree.
* `THIRD_PARTY_LICENSES.md` is unaffected — it is generated by
  `cargo-about` from the **dependency** set, and this Pass adds zero
  dependencies (see §5).

## 2. The metaphor-not-artwork rule (binding on every future icon here)

The operator's instruction — *"try to make them close to what inkscape
and Adobe use for similar commands without running into copyright
issues"* — draws the line this directory is held to:

* **Allowed: metaphor-level resemblance.** A magnifier means zoom. A
  curved arrow means undo. Scissors mean split. Corner brackets mean fit
  to frame. These are industry conventions with no single author, and
  matching them is what makes a toolbar legible to someone arriving from
  Acrobat or Inkscape.
* **Forbidden: asset-level copying.** No tracing, no importing, no
  "adapting" of any Adobe or Inkscape SVG, icon font, or screenshot.
  Every glyph in this directory was constructed from primitives
  (rectangles, circles, line segments, arcs) against the coordinates in
  ui-spec §3, and every file says in a comment which concept it depicts.
* This mirrors the standing project rule that Acrobat and Inkscape are
  **behavioural** references only, never sources of GUI structure or
  art (project `CLAUDE.md` rules 12 and R61).

Note that this rule is *stricter* than copyright law strictly requires
for simple geometric glyphs. That is deliberate: it removes the question
entirely rather than leaving a judgement call in a file nobody will
re-examine.

## 3. Style contract (every file here obeys it)

Reverse-engineered from the ScripTree set in ui-spec §1 and reproduced
verbatim by every asset below:

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 48 48" fill="none" aria-hidden="true">
  <!-- Generic <concept> shape — placeholder, not a vendor trademark logo -->
  <path|rect|circle … stroke="currentColor" stroke-width="2.5"
        stroke-linecap="round" stroke-linejoin="round"/>
</svg>
```

* **48x48 viewBox**, content inset ~6–8 units from every edge.
* **`fill="none"`, `stroke="currentColor"`** — pure outline, no baked
  colour. This is the property `crates/pdfce-gui/src/icons.rs` relies on
  to rasterize one mask per icon and tint it per theme/state; an asset
  with a hardcoded colour would break light/dark theming structurally.
* **`stroke-width="2.5"`**, round caps and joins throughout.
* A one-line comment naming the concept and disclaiming trademark risk.

### The one deliberate exception

`redact.svg` is the only asset with a **filled** shape
(`fill="currentColor"` on the redaction bar). ui-spec §8.1 makes this an
explicit, rule-based exception, not style drift: a solid bar is what
redaction actually leaves behind, and an outline-only glyph would
visually understate a feature that irreversibly removes content
(R35/R52/R58). **A future icon audit must not "fix" it back to an
outline.** `icons.rs`'s `redaction_is_the_only_filled_icon` test asserts
both halves of this — that redaction is filled and that nothing else is.

`shape-highlight.svg` uses `stroke-width="1"` for its 45° hatch. Also
deliberate (ui-spec §3.3): the hatch is a *texture* standing in for
translucent highlighter colour, not a contour, and at 2.5 it would fill
the band solid and read as redaction.

## 5. Deviations from the ui-spec, recorded

The standing convention is that the engineer implements a UI spec and
deviates only with a recorded reason. Three deviations:

1. **`edit-objects.svg` is an addition the spec does not cover.** The
   ui-spec was written 2026-08-01 and audited the toolbar as it then
   stood; the Pass 9c-min "Obj" vector-edit toggle shipped afterwards.
   Leaving the one remaining control on a bare Unicode glyph would have
   defeated the point of the Pass, so the icon was authored in the same
   §1 contract. Its metaphor (a path with draggable nodes) is chosen to
   collide with nothing: not `edit.svg`'s pencil (page **text**), not
   `markup.svg`'s shapes (annotation **authoring**).
2. **Icon size is 16 pt, not the 18–20 px ui-spec §4.1 suggests.** That
   paragraph contradicts itself — `ICON_BUTTON_SIZE` is 28x24 pt and
   egui's default `button_padding` is (4,1), so the content box is 20x22
   pt and 18 pt leaves 1 pt, not the "few px of padding on every side"
   the same sentence asks for. 16 pt satisfies both halves and pairs
   optically with egui's 12.5 pt body text on the icon+text controls.
   Rationale is repeated at `icons::ICON_PTS`.
3. **The rail's keyboard reorder arrows (▲/▼) keep their Unicode
   glyphs.** The ui-spec's mapping covers the toolbar and Tools dock and
   assigns them nothing. Rather than invent art the spec has not
   reviewed, they still go through the same accessible-name wrapper
   (`PdfceApp::glyph_button`), so nothing about them regressed.

## 6. Rendering, and why no new dependency appears here

These SVGs are **not** rasterized by any SVG library. `icons.rs` parses
the subset of the path/rect/circle grammar these files use and strokes
it with `tiny-skia`, which pdfce already depends on via `pdfce-render`.
Zero Cargo dependencies were added for this icon set — in particular
`resvg`/`usvg` (MPL-2.0) was considered and **rejected** by the
operator, and pre-rasterizing to PNG at build time was rejected because
it bakes in a resolution and, on this machine, had no working SVG
rasterizer to run.

Practical consequence for anyone editing a file in this directory: the
parser refuses anything outside its subset rather than guessing, and
`icons.rs`'s `every_icon_parses` / `every_icon_rasterizes_to_visible_pixels`
tests parse and rasterize every asset. **A new or edited icon that uses
`<g>`, `<defs>`, a `transform`, a gradient, CSS, or an unsupported
`stroke-linecap` value will fail `cargo test`, not fail silently at
runtime.** Add new [`Icon`] variants to `Icon::ALL` or they ship
unverified.
